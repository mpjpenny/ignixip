What a PTR record is

Forward DNS answers which address a name uses. An A record does that for IPv4, and an AAAA record for IPv6. Reverse DNS asks which name an address claims. The record type is PTR. RFC 1035 puts IPv4 reverse names under in-addr.arpa, with the octets reversed. For the documentation address 203.0.113.10 the query is 10.113.0.203.in-addr.arpa. IPv6 reverses the nibbles under ip6.arpa, as RFC 3596 defines.

Publish one hostname you control, such as mail.example.com. If several PTRs exist, the lookup on this site shows the first answer it receives.

Why a receiving server looks

Many mail servers refuse or slow mail when the connecting address has no PTR, or when that name does not point back at the address. The second step is forward-confirmed reverse DNS. Look up the PTR, then look up A or AAAA for the name it returned. The original address has to be one of those answers. RFC 1912 says the PTR and the address record should match. A name that points somewhere else fails in the same way as a missing record.

Gmail's sender guidelines require a PTR whose hostname resolves back to the sending address. The sender FAQ uses 4.7.23 when Gmail rate-limits a missing or mismatched PTR, and 5.7.25 when it refuses the message. That rejection often never appears in a DMARC report, because the session ended first.

SMTP does not require that refusal. RFC 5321 says the EHLO name must be a primary hostname, a name with an address record, or an address literal when the host has none. A server may check that the name matches the client address, but it must not refuse the message only because that match failed. Refusing for a missing PTR is the receiver's own policy, which many operators apply.

Look it up

Use the sending address from the bounce, not the computer you read mail on. The full IP lookup prints a Reverse DNS row.

  • A name and FCrDNS. A PTR was found, and a forward lookup of that name returned this address.
  • A name and "no forward match". A PTR was found, and the name did not return this address.
  • No PTR record. The reverse query returned nothing.

The check uses a public resolver. IPv4 is confirmed with A, IPv6 with AAAA. See the row on a known address: /?tab=ip&ip=8.8.8.8&full=1. 8.8.8.8 is a public resolver, not a mail server. Replace it with your sending address. full=1 keeps you on that report. Without it, an address this site already publishes opens as its own page, which does not show the forward-confirmed mark. Then read the hostname with the DNS lookup, for example /?tab=dns&q=dns.google. The name in the PTR needs an A or AAAA that is the sending address. The short IP lookup can show a hostname. It does not show the FCrDNS mark.

Who sets it, and how to fix it

The reverse zone belongs to the network that holds the address: the host, the VPS provider, or the ISP. It is not your domain's zone. A PTR typed in next to SPF, at the company that hosts example.com, does nothing unless they also hold the address and have delegated the reverse zone to you. That delegation is uncommon.

  1. Choose a hostname in a zone you control, usually mail.example.com. Gmail asks for a reverse name in your domain, not only a name the provider generated.
  2. Publish the forward record at your DNS host first. For IPv4 that is mail.example.com. A 203.0.113.10, with your address instead of the documentation address. Add AAAA if the server connects over IPv6. Many providers refuse the PTR until this record already points at the address. Check it with the DNS lookup.
  3. Ask the IP provider to set the PTR to that hostname. The panel may say rDNS, reverse DNS, or PTR. This is a ticket on the server account, not a record at your DNS host.
  4. Set the server's EHLO name to that hostname. Receivers compare the announced name with the PTR. A PTR that confirms under a different name still fails them.
  5. After the TTL, open the IP lookup again and look for FCrDNS. A new cloud address needs the PTR set again.

If the provider will not set a PTR, which is normal on a home connection and on some shared hosts, you cannot repair it in your DNS. Send through a host that already has reverse DNS. Editing SPF will not clear the rejection. The blacklist guide reaches the same conclusion for a policy range: that address should not be the one opening port 25.

SPF, DKIM, DMARC, and the HELO name

A correct PTR does not make the other checks pass. A pass on the others does not satisfy a receiver that requires forward-confirmed reverse DNS.

  • The PTR names the connecting address. It does not authorise a domain.
  • SPF lists addresses allowed to use a domain in the envelope. It does not read the PTR. The ptr mechanism inside an SPF record is a different thing, and RFC 7208 says not to use it. The SPF guide covers that. Adding it does not publish a PTR.
  • An empty envelope sender is how a bounce is sent. RFC 7208 then treats the MAIL FROM identity as postmaster at the EHLO hostname. That name needs an SPF record which includes this server, or the bounce fails SPF while ordinary mail passes. v=spf1 a -all is enough when the name's own address is the server.
  • DKIM signs the message. It does not look at the PTR. A rejection for a missing PTR can happen before the signature is checked.
  • DMARC passes only when SPF or DKIM passed and aligned with From. The DMARC guide is that rule. Gmail asks for the DNS match and for authentication. Neither replaces the other.
  • The EHLO name, still often called HELO, should be the PTR name. The header guide shows where a receiver recorded the name the client claimed. That claim is not the PTR. When they differ, change the server so it announces the PTR name.

The mail authentication check describes SPF, DKIM, and DMARC. It does not read the reverse zone. Use the IP lookup for the PTR.
